# 数字人文本流式与音频播报实现方案

## 1. 文档概述

本文档说明 `digital-human` 项目当前数字人文本流式回复、语音合成、分段预取、顺序播放、跟读展示以及中断处理的实现方案。

当前总体采用：

> Dify SSE 文本流式接收 + 播报文本动态分段 + 最多两路 TTS 并发预取 + 音频严格顺序播放 + 音频进度驱动文字跟读。

## 2. 整体处理流程

```text
用户发送问题
  ↓
POST /v1/chat-messages
response_mode: streaming
  ↓
前端通过 ReadableStream 持续读取 SSE 数据
  ↓
合并文本增量，解析思考内容、正文和播报文本
  ↓
正文持续更新，播报文本按规则动态切段
  ↓
最多并发请求两个 /xiren-api/v1/audio/speech
  ↓
TTS 返回音频 Blob，转换为 Blob URL
  ↓
按照 sequence 严格顺序播放
  ↓
播放进度驱动正文跟读、进度条和人物 speaking 状态
  ↓
Dify、TTS 和播放队列全部结束后恢复 idle 状态
```

## 3. 文本流式实现

### 3.1 Dify 请求

前端通过 `/v1/chat-messages` 发起问答请求，请求体中的 `response_mode` 固定为 `streaming`。

主要请求字段包括：

- `query`：用户问题。
- `inputs`：Dify 工作流输入参数，当前为空对象。
- `user`：当前浏览器会话的稳定用户标识。
- `conversation_id`：存在历史会话时继续携带。
- `response_mode`：值为 `streaming`。

请求使用 `Authorization` 和 `Content-Type: application/json` 请求头，并通过 `AbortController` 支持主动取消。

### 3.2 SSE 数据读取

流式响应使用以下浏览器能力读取：

- `response.body.getReader()` 获取数据流读取器。
- `TextDecoder` 将二进制数据转换为文本。
- 使用空行 `\n\n` 拆分完整 SSE 事件。
- 提取每个事件中的 `data:` 内容。
- 忽略 `[DONE]` 和 `ping` 事件。

前端会保留尚未接收完整的尾部缓冲区，等待下一批数据后继续拼接，避免半个 JSON 事件被错误解析。

### 3.3 流式文本合并

当前兼容两种返回形式：

1. 增量文本：将新片段追加到已累计文本后。
2. 全量文本：如果新内容已经包含旧内容，则直接使用新内容。

当 Dify 返回 `message_replace` 事件时，使用本次文本直接替换累计内容。

同时持续保存：

- `task_id`：用于主动停止 Dify 任务。
- `conversation_id`：用于延续上下文会话。
- `message_id`：用于标识本次 Dify 消息。

### 3.4 内容解析

每次文本变化后，前端会将原始回复解析为：

- `thinkMarkdown`：`<think>...</think>` 中的思考内容。
- `bodyMarkdown`：用户可见的 Markdown 正文。
- `speechText`：从正文 Markdown 转换出的纯文本，用于 TTS。

Markdown 在显示前通过 `marked` 渲染，并使用 `DOMPurify` 清理不安全 HTML。

## 4. 文本展示策略

当前文本接收和文本展示是两个相关但独立的过程：

- `latestBodyMarkdown` 保存已经收到的完整 Markdown 正文。
- `streamSpeechText` 保存当前可用于语音播报的纯文本。
- `displayedSpeechText` 保存已经跟随音频进度展示的文本。

音频播放过程中，正文按照当前播放段和音频播放比例逐步显示，实现文字跟读效果。

整轮音频播放完成后，再恢复最终完整 Markdown 正文，保证表格、列表和格式化内容正确显示。

如果 Dify 不可用，则使用本地兜底回复，并通过定时器逐字模拟文本流式输出，同时继续复用相同的 TTS 分段和播放队列。

## 5. TTS 分段策略

### 5.1 文本预处理

播报前会统一处理：

- Windows 和 Unix 换行符。
- 多余 Markdown 加粗符号。
- 行尾和行首空格。
- 连续空行。
- 段落之间自动补充句号。
- 普通换行自动补充逗号。

这样可以减少 TTS 对 Markdown 标记和异常换行的错误朗读。

### 5.2 首段规则

首段以尽快开始播报为目标：

- 目标长度：24 个有效字符。
- 达到目标后最多向后查找 12 个有效字符。
- 优先在句号、问号、感叹号和分号等句末标点处切分。

### 5.3 后续分段规则

第二段及后续分段使用：

- 目标长度：50 个有效字符。
- 达到目标后最多向后查找 20 个有效字符。
- 优先在句末标点处切分。

有效字符统计会忽略空白字符。

Dify 流结束后，不足目标长度的尾部文本会立即作为最后一段加入 TTS 队列，避免遗漏尾段。

## 6. TTS 请求方案

TTS 接口使用 JSON 请求：

```json
{
  "input": "需要播报的文本",
  "model": "运行时配置中的模型",
  "voice": "serena",
  "response_format": "mp3",
  "speed": "1.0"
}
```

请求特点：

- 请求方法：`POST`。
- 请求头：`Content-Type: application/json`。
- 请求地址：运行时配置生成的 `/xiren-api/v1/audio/speech` 地址。
- 通过 `AbortSignal` 支持取消。
- 接口返回完整音频 Blob，不是真正的音频字节流播放。

收到音频 Blob 后，前端使用 `URL.createObjectURL(blob)` 生成临时音频地址。

音频被替换、播放结束、流程取消或组件卸载时，会调用 `URL.revokeObjectURL` 释放资源。

## 7. TTS 并发预取

当前 TTS 最大并发请求数为 2。

```text
第一段形成 → 请求第一段 TTS → 开始播放第一段
第二段形成 → 请求第二段 TTS → 缓存在播放队列
第一段结束 → 立即播放第二段
第三段形成 → 空闲请求槽位继续预取第三段
```

这种方式允许“当前段播放”和“下一段合成”同时进行，用于减少第一段和第二段之间的停顿。

所有正在进行的 TTS 请求通过 `Set<AbortController>` 管理，可以在打断、新问题或流程取消时一次性终止。

## 8. 音频顺序控制

每个 TTS 分段都会分配递增的 `sequence`。

TTS 请求可以并发返回，但播放必须满足：

```text
item.sequence === nextPlaybackSequence
```

因此即使第二段音频先于第一段返回，也只会进入缓存队列，不会抢先播放。

第一段播放结束后，`nextPlaybackSequence` 更新为下一序号，然后继续消费播放队列。

## 9. 音频播放和进度同步

真实音频使用浏览器 `HTMLAudioElement`：

```text
new Audio(blobUrl)
```

播放过程监听：

- `onended`：当前段正常结束。
- `onerror`：音频失败时结束当前段并继续流程。

前端每 120ms 计算一次播放进度：

- 如果可以获取真实音频时长，则使用 `currentTime / duration`。
- 如果无法读取音频时长，则使用文本估算时长计算进度。

播放进度同时驱动：

- 当前段文字跟读位置。
- 整条回复的总体播放进度。
- 消息进度条。
- 数字人 speaking 状态。

## 10. 音频失败兜底

TTS 请求失败且不是主动取消时，会生成本地模拟语音结果。

当结果没有真实 `audioUrl` 时：

1. 优先调用浏览器 `SpeechSynthesisUtterance` 进行中文朗读。
2. 浏览器语音不可用时，按照估算时长推进并结束当前段。

这可以保证某一段 TTS 请求失败时，后续播放流程不会永久卡住。

## 11. 流程结束条件

只有同时满足以下条件，当前问答流程才会结束：

- Dify 文本流已经结束。
- TTS 待合成队列为空。
- 没有正在执行的 TTS 请求。
- 音频播放队列为空。
- 没有正在播放的音频段。

满足后：

- 恢复最终完整 Markdown 正文。
- 将消息标记为已完成。
- 数字人状态恢复为 `idle`。
- 清理播放和进度状态。

## 12. 中断和过期结果保护

当前使用两层机制避免旧请求污染新会话。

### 12.1 AbortController

用于取消：

- Dify 流式请求。
- Dify 后端任务。
- 所有并发 TTS 请求。
- 当前音频播放。

### 12.2 flowId

每次新问题、主动打断或流程重置都会更新 `flowId`。

所有异步回调在更新界面或加入播放队列前，都会检查自身 `flowId` 是否仍为当前流程。

即使旧请求未能及时取消，其晚到结果也会被丢弃，并释放对应音频资源。

## 13. 异常处理

- Dify 返回部分文本后异常：保留已有内容，并继续完成已有文本的 TTS 播报。
- Dify 未返回正文即异常：切换为本地兜底回复。
- TTS 单段失败：使用本地模拟语音结果，继续后续队列。
- 主动取消：不显示为真实错误。
- 新问题到来：先取消上一轮 Dify、TTS 和播放流程，再开始新流程。

## 14. 主要实现文件

- `src/hooks/useDifyChat.ts`：Dify 请求、SSE 解析、文本合并和停止任务。
- `src/hooks/useDigitalHumanDemo.ts`：问答流程、文本分段、TTS 并发队列、播放顺序和中断状态。
- `src/hooks/useSpeechSynthesis.ts`：TTS JSON 请求、Blob URL 和资源释放。
- `src/components/VideoDigitalHumanStage.vue`：真实音频播放、浏览器语音兜底和进度上报。
- `src/utils/message-content.ts`：思考内容拆分、Markdown 渲染和播报纯文本提取。
- `src/config/runtime-config.ts`：Dify、TTS、音色和超时等运行时配置。

## 15. 当前方案特点

### 优点

- 第一段可以较早开始播报。
- 第二段能够在第一段播放时提前合成。
- TTS 响应乱序不会导致音频播放乱序。
- 支持完整的取消、打断和过期结果保护。
- 文本跟读、音频进度和数字人状态保持同步。
- 单个外部服务失败时具备兜底能力。

### 限制

- TTS 服务返回完整 Blob，不是真正的流式音频。
- 段落之间仍可能受到后端合成耗时和网络延迟影响。
- 当前最多并发两个 TTS 请求。
- 播报期间正文显示受到音频播放进度控制，而不是完全独立的文字流式展示。

## 16. 结论

当前实现属于“文本真正流式、音频分段准流式”的方案。

Dify 文本通过 SSE 实时到达；音频并非边接收字节边播放，而是在文本达到分段条件后请求完整音频 Blob，通过两路并发预取和严格顺序播放降低等待时间。
